# Claude 审查任务

## 目标与范围

对 2026-10-28 v3 做独立代码审查，找出真实缺陷、要求覆盖缺口和证据不足，给出可执行的修改方案。把成果写入仓库，方便所有者直接阅读文件。本轮只写审查文档，保留运行代码和测试不变。

## 执行步骤

1. 阅读根目录 CLAUDE.md 指定文档；记录实际基准提交编号、环境和已读文件。在有 Git 写权限时创建 `review/v3-audit` 分支；若同名分支存在则检查其状态，避免覆盖他人工作。
2. 按调用链检查数据读取、字段映射、时间与设备划分、特征构造、标签与随访、训练、CV、阈值选择、诊断、候选采纳、恢复和 TEST 隔离。每个确认问题给出文件/行号、触发条件、影响与证据；不能把设计偏好当错误。
3. 重点核查：未来信息泄漏；折外训练/权重/标签污染；分支与基线队列是否一致；漏报分类是否重复计数；探索预算恢复是否重复扣除；缓存哈希与表示兼容；模型复用身份；Agent 提示词是否实际进入调用；动态特征执行隔离；成本统计完整性。
4. 检查 tests/ 后运行可负担的离线测试。仅使用合成数据和模拟接口。记录实际命令与结果；没有跑的测试写明原因。禁止为了使测试通过而修改测试或源码，本轮无需新增测试文件。
5. 建立 R01–R12 与 C01–C07 全覆盖矩阵，状态使用：满足、部分满足、不满足、待验证。每项列出代码/文档证据、缺口、下一步，避免所有项目只引用同一份 README。
6. 将结果写入下列三份文档，按严重程度和实施依赖排序。完成后检查跨文档问题编号一致，文档匿名化且不含秘密。在独立分支提交并推送文档（权限允许时）；不要合并到主分支。

## 必须交付

- `docs/review/FINDINGS.md`：摘要；基准提交；检查范围；实际测试；问题表（ID、严重度、确认/待验证、位置、复现、影响、证据）；未覆盖范围。没有确认问题也要如实说明，不能凑数。
- `docs/review/CHANGE_PLAN.md`：对应问题 ID、具体待修改文件/函数、预期行为、方案取舍、兼容性与迁移、验证方法、工作顺序、所需数据/资源；单独区分必要修复与可选研究。注明“待所有者确认，尚未实施”。
- `docs/review/REQUIREMENTS_MATRIX.md`：覆盖全部 R/C 编号的状态、证据与后续行动。

## 执行边界

不运行全量训练，不调用付费模型 API，不登录服务器，不下载真实数据，不接触独立 TEST 来调参，不改旧实验状态。任何需要这些动作的验证都在方案中标明输入、预算和预期判据。

如果只有读取能力：明确说明无法写仓库，并输出三份文档的完整内容供所有者保存；绝不能声称文件已保存、提交或推送。

## 完成标准

三份文档已写入；所有需求编号覆盖；确认缺陷都有可定位依据；每项修改计划关联发现或需求缺口；真实执行与待验证事项分开；文末提供实际提交编号和保存路径。只在聊天里说“已检查”不算完成。
